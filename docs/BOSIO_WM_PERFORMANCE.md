# BOSIO 구면 윈도우 매니저 성능 측정

## 현재 BS25 보드 검증

현재 기본 비트스트림은 DDR 셀 데이터와 64바이트 라인·16KiB·2-way 캐시를
사용한다. PYNQ-Z2, M=16, 100MHz에서 다음을 확인했다.

| 항목 | 결과 | 측정 범위 |
|---|---:|---|
| 전체 구면 장면 | 4,220타일, 1,098,240바이트 | 고정 색으로 채운 M=16 전체 구면 |
| 고정 자세 출력 스트림 | 59.92 FPS | RTL 프레임 카운터, 약 2초·120프레임 |
| 센서 자세 출력 스트림 | 59.92 FPS | RTL 프레임 카운터, 약 2초·120프레임 |
| 고정 자세 캐시 히트 비율 | 99.862% | 이 장면과 읽기 주소 패턴에서의 결과 |
| 한 타일 부분 갱신 | 평균 15.0ms | 96워드 BPT1, 8회, 프레임 경계 대기 포함 |

출력 스트림 FPS는 앱 이미지 생성·IPC·창 합성을 포함하는 장면 갱신 FPS가
아니다. 부분 갱신 시간도 이미 만들어진 BPT1의 드라이버 적용 시간이며,
앱 전체 처리율로 환산하면 안 된다. 두 DDR 버퍼의 변경 내용과 주소 교체를
확인했다. 캡처보드는 이 검증에서 사용하지 않았다.

M=32는 전체 구면 패킹(1,084,800워드)만 확인했다. 실제 출력과 앱 합성 성능은
아직 측정하지 않았다. 상세 설정·제약은 [DDR 캐시 문서](BOSIO_DDR_CACHE.md),
원본은 [보드 측정 JSON](../verification/results/bosio_ddr_cache_board_validation.json)에 있다.

## 이전 최적화 과정의 측정 기록

이하 표는 DDR 캐시 도입 전 BRAM 장면 캐시에서 측정한 결과다. 초기 NumPy,
C++/NEON, 직접 패킹, 부분 타일 갱신의 개선 과정을 남긴다. 당시의 AA·합성
경로·패치 크기가 현재와 다르므로 BS25의 현재 앱 FPS로 해석하거나 위 결과와
직접 비교하면 안 된다. 표의 `DMA ms`는 당시 전송 경로와 장면 교체 대기 시간이다.

### 초기 NumPy 측정 조건

- 보드: PYNQ-Z2, Zynq-7020
- 구면 격자: `M=16`
- 전체 작은 삼각형 셀: `20 × 211 × 16² = 1,080,320`
- HDMI: 1280×720, 목표 60 Hz
- 센서 모드: GY-521 직접 RTL 스트림 활성화
- 데몬 제한: 측정 중 240fps로 높여 소프트웨어 처리량을 제한하지 않음
- 각 조건: 애플리케이션이 연속 갱신 요청을 보내는 약 4초 구간
- 합성: Python/NumPy ARM CPU
- pack+DMA: `pack_scene()`과 출력 코어 장면 교체 완료 대기 포함

`scene update FPS`는 애플리케이션의 새 창 장면이 정이십면체 framebuffer로
합성되고 DMA 교체까지 완료된 비율이다. HDMI scanout FPS와 구분해야 한다.

### 초기 NumPy 실측 결과

| 조건 | 창 | 구면 셀 합집합 | 활성 타일 | 합성 ms | pack+DMA ms | 장면 갱신 FPS | HDMI FPS |
|---|---:|---:|---:|---:|---:|---:|---:|
| 창 없음, 포인터 연속 이동 | 0 | 포인터만 | 소수 | 325.7 | 138.5 | **1.96** | 58.76 |
| FOV 25% 창 | 1 | 16,924 | 84 | 1,021.7 | 149.2 | **0.86** | 60.51 |
| FOV 50% 창 | 1 | 33,186 | 158 | 1,021.7 | 140.7 | **0.85** | 59.37 |
| FOV 100% 창 | 1 | 65,648 | 304 | 1,074.3 | 137.6 | **0.82** | 60.12 |
| FOV 100%, 304×192 RGB 전체 IPC | 1 | 65,648 | 304 | 1,069.2 | 160.6 | **0.81** | 59.69 |
| 네 창으로 FOV 전체 구성 | 4 | 68,380 | 310 | 3,200.2 | 146.1 | **0.30** | 60.13 |
| FOV 전체 크기 창 8개 중첩 | 8 | 65,648 | 304 | 6,531.2 | 134.2 | **0.15** | 60.13 |

네 창과 여덟 창 조건은 한 장면 합성 시간이 길어 각각 2회와 1회 완료값을
사용했다. 합성 시간과 관측 FPS가 서로 일치하므로 당시 처리량의 규모를
판단하는 데는 충분하지만 장기 통계로 보려면 측정 시간을 늘려야 한다.

### 초기 결과의 해석

정적인 창을 바라보거나 GY-521로 시점을 회전하는 경우 HDMI와 출력 코어가
약 60fps를 유지한다. 센서 회전은 FPGA가 기존 구면 장면을 다시 투영하므로
Python 윈도우 합성 FPS의 영향을 받지 않는다.

당시 창 내용 갱신, 포인터 이동, 창 드래그는 새 장면 DMA가 필요했다. 초기 구현은
창 하나를 그릴 때마다 108만 개 셀 전체에 대해 세 번의 dot product와 mask를
다시 계산한다. 따라서 창이 차지하는 면적보다 창 개수가 성능을 지배한다.
25%와 100% FOV 창의 합성 시간이 거의 같은 이유도 이것이다.

pack+DMA는 약 134~161ms로 비교적 일정했다. 가장 큰 병목은 창당 약
0.8~1.0초가 드는 Python 구면 투영이었다. 당시에는 동영상 창, 부드러운
포인터와 실시간 창 드래그 용도로 사용하기에 장면 갱신 속도가 부족했다.

### 당시의 최적화 계획

1. 창 위치나 각 크기가 바뀔 때만 셀 index와 texture 좌표 LUT를 계산하고,
   표면 내용 갱신에서는 LUT를 재사용한다.
2. 창과 교차하는 정이십면체 face·tile만 계산하도록 공간 인덱스를 둔다.
3. 여러 애플리케이션 갱신을 한 번에 적용하는 frame transaction API를 둔다.

### C++/NEON 적용 결과

창별 투영 LUT, NEON dot product와 포인터 mask, NEON RGB888→RGB332 패킹을
C++17 공유 라이브러리로 구현한 뒤 같은 조건으로 다시 측정했다. NumPy 참조와
1,080,320셀 합성 결과가 전부 일치했고, M=8/16/32 packed scene도 word 단위로
일치했다.

| 조건 | NumPy FPS | C++/NEON FPS | 향상 | C++ 합성 ms | C++ pack+DMA ms |
|---|---:|---:|---:|---:|---:|
| 창 없음, 포인터 이동 | 1.96 | **8.98** | 4.6배 | 81.3 | 23.1 |
| FOV 25% 창 | 0.86 | **19.40** | 22.6배 | 22.3 | 24.0 |
| FOV 50% 창 | 0.85 | **19.72** | 23.3배 | 23.4 | 22.0 |
| FOV 100% 창 | 0.82 | **18.73** | 22.7배 | 25.8 | 22.1 |
| FOV 100%, 전체 RGB IPC | 0.81 | **16.59** | 20.6배 | 27.8 | 26.4 |
| 네 창으로 FOV 구성 | 0.30 | **17.71** | 59.2배 | 26.1 | 25.0 |
| 전체 FOV 창 8개 중첩 | 0.15 | **11.83** | 78.7배 | 51.7 | 26.7 |

창 내용 변경은 캐시된 LUT를 사용하므로 창 개수 증가가 이전처럼 전체 구면 dot
product 반복으로 이어지지 않게 되었다. 당시 포인터는 움직일 때마다 구면 전체
mask를 새로 만들어 8.98fps였다. 이후 부분 타일 갱신은 아래 단계에서 추가했다.
별도 하드웨어 포인터 overlay나 GPU 합성은 현재 구현에 포함되지 않는다.
현재 기본 서비스는 포인터의 시각적 표시를 숨긴다.

원시 측정 데이터는 [초기 NumPy 결과](../verification/results/bosio_wm_benchmark.json)와
[C++/NEON 결과](../verification/results/bosio_wm_benchmark_neon.json), 실행 도구는
[bosio_wm_benchmark.py](../sw/bosio_wm_benchmark.py)에 있다.

### RGB332 직접 장면 생성 결과

두 번째 최적화에서는 C++ 합성기가 24비트 RGB 구면 이미지를 만든 뒤 다시
RGB332로 변환하던 중간 단계를 제거했다. 창 surface는 변경될 때 한 번만
RGB332 index로 변환하고, 매 프레임에는 캐시된 투영 LUT를 이용해 출력 코어의
palette, tile directory, 활성 tile payload를 바로 생성한다. Python 데몬은 이
packed word 배열을 DMA에 전달한다.

| 조건 | 이전 C++/NEON FPS | 직접 packed FPS | 추가 향상 | 직접 합성 ms | DMA ms |
|---|---:|---:|---:|---:|---:|
| 창 없음, 포인터 이동 | 8.98 | **10.85** | 1.21배 | 71.6 | 13.8 |
| FOV 25% 창 | 19.40 | **29.72** | 1.53배 | 14.3 | 14.2 |
| FOV 50% 창 | 19.72 | **29.72** | 1.51배 | 15.7 | 12.9 |
| FOV 100% 창 | 18.73 | **29.34** | 1.57배 | 18.0 | 11.1 |
| FOV 100%, 전체 RGB IPC | 16.59 | **19.64** | 1.18배 | 18.8 | 15.3 |
| 네 창으로 FOV 구성 | 17.71 | **29.38** | 1.66배 | 18.0 | 11.0 |
| 전체 FOV 창 8개 중첩 | 11.83 | **19.64** | 1.66배 | 38.2 | 7.4 |

`DMA ms`는 직접 packed 경로에서는 패킹을 포함하지 않고 출력 코어의 장면
교체 완료 대기까지 포함한다. 창이 없는 포인터 측정은 포인터가 움직일 때마다
전체 구면 mask를 다시 계산해 당시에도 비효율적이었다. 이 단계에서는 포인터
mask의 국소 갱신과 애플리케이션 surface용 공유 메모리를 후속 과제로 검토했다.

직접 packed 결과 원본은
[직접 패킹 측정 JSON](../verification/results/bosio_wm_benchmark_direct_packed.json)에 있다.

### Dirty tile 및 BS23 RTL 부분 갱신 결과

`BS23` 출력 코어에는 `BPT1` 부분 타일 DMA를 추가했다. 소프트웨어는 창별
dirty rectangle을 누적하고 캐시된 투영 LUT에서 해당 source 영역을 참조하는
셀만 다시 합성한다. 창 이동, 포커스, z-order, 포인터 및 타일 활성 구조가
달라지면 전체 snapshot으로 자동 전환한다.

전체 FOV 창의 16×16 RGB 영역을 60 Hz로 변경하는 5초 paced test 결과는
다음과 같다.

| 항목 | 결과 |
|---|---:|
| 애플리케이션 갱신 요청 | 300회 |
| 실제 합성 완료 | 296회 |
| 실제 타일 패치 | 292회 |
| RGB332 결과가 같아 생략 | 4회 |
| 평균 합성 시간 | 8.92 ms |
| 평균 부분 DMA 시간 | 3.61 ms |
| 평균 패치 크기 | 496 words |
| HDMI 관측 FPS | 58.47 |

이 조건의 실제 변경 패치 처리율은 측정 본구간 5초 기준 58.4 FPS다. 동일 장면의
전체 snapshot은 23,936 words였으며 16×16 변경은 6개 구면 타일, 496 words로
줄어 전송 word 수가 약 48배 감소했다. 연속 최대 부하에서도 네 창 구성은 약
62.8 render FPS, 전체 FOV 창 8개 중첩은 약 58.8 render FPS를 처리했으며 HDMI는
약 60 FPS를 유지했다.

당시 BS23 RTL은 먼저 비활성 BRAM bank에 패치를 적용하고 프레임 경계에서 교체한 뒤 같은
패치를 이전 bank에 재적용한다. 연속 패치가 누적되어도 두 bank의 기준 장면이
달라지지 않으며 화면 중간 교체도 발생하지 않는다.

원시 결과는 [부분 타일 결과](../verification/results/bosio_wm_benchmark_partial_tile_16.json)와
[60 Hz paced 결과](../verification/results/bosio_wm_benchmark_paced_16.json)에 있다.
현재 BS25는 이 BRAM 복제 대신 드라이버가 DDR 버퍼를 수정하고 코어가 주소를
전환한다. 위 6타일·496워드·5초 실험과 현재 1타일·96워드·8회 실험은 조건이 다르다.
